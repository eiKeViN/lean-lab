# Registered comparison, 2026-11-11

**Question.** On a substantial Lean development, what does preinstalling and
activating SHEAF add to a clean, goal-directed coding agent with equal tools
and dependencies? This is an exploratory case study on one mathematical
project. Two independent runs per arm describe stochastic variability.

**Change after auditing, before any participant saw the task.** The proposed
HGP length, dimension and distance statements are already proved together in
QECert at c0ff74952c65b48e2ba5430fc4dfa4459d120440,
QEC/Results/QLDPC/HypergraphProductParameters.lean. Both groups receive that
library. The added long target connects erasures, supported quotient classes,
restricted ranks, CSS distance, HGP strips and concrete instances. The
[1,1] example is [[5,1,2]]. The 2-by-2 repeated-row example is [[8,2,2]].
The two blocklengths and both sector profiles were independently enumerated.
The repository audit found related cleaning and shortening material but no
end-to-end strip profile in the checked HGP modules. This is a bounded audit.

**Participants.** Four independent GPT-6.1 Sol/high root sessions. Spawned
roles inherit the identical explicit model/effort assignment; provider model
fallback is disabled. No account memory, account tools, Internet, other runs,
repository history of this experiment, or supervisor notes are exposed. The
two arms share the versioned packet, blank Lean project, Lean/mathlib/QECert,
generic Linux/Lean tools, and the same host-provided multi-session interface.
SHEAF is frozen at ee75eba0f29643aafb51bca895a85d09d45e6691. A opens at its
upstream root, reads its launcher instructions, and can set up its project
using the unedited template. Its administrative setup answers are given up
front. B opens in the ordinary workspace with the common task. The shell
always starts at /work. Linux process isolation, offline per-run writable
worktrees, ephemeral threads, a generic shell tool and managed independent
sessions implement the control plane. SHEAF's launcher, maintainer, lead and
workers use the same host session interface in place of interactive tmux
terminals. This is a transport adaptation. No decision about proof order,
DAG, or division of mathematical labor is supplied to B.

**Budget and scheduling.** Each run ends on completion of all its agents,
60 minutes of monotonic clock time, or 12,000,000 weighted usage units across
all threads, whichever comes first. Units are cached input + 8 × uncached input
+ 16 × output, inclusive of reasoning output; output is counted once. This
is a registered proxy for inference usage, not a dollar price. Report raw
categories as well. Up to four concurrent model sessions per run, counting
the launcher. All four runs start after the same dependency smoke check.
Two disjoint CPUs per room for shell work, on one nine-CPU host. Start order
and paired assignments are determined by a seeded shuffle (seed 20261111).
Report actual start offsets, interruption, usage overshoot and contention.
Limits are enforced on usage notifications; a call in flight can overshoot.
A non-final snapshot strictly below a budget is the conservative estimate
when two sides straddle a threshold.

**Outcomes frozen before exposure.** Primary outcome is full independent
acceptance of A–E by the cap. Secondary report is individual milestones A
(HGP), B (both rank identities and complementary identities), C (syndrome
ambiguity iff and distance), D (the two universal strip formulas) and E
(both concrete calls). A mathematical milestone must cover every claim in
its section. Report individual accepted subresults for partial submissions
and record a missed endpoint as censored. No credit for number of commits,
lines, DAG nodes, or unsupported claims. Compare the common budget checkpoints
3M/6M/9M/12M and final wall-clock snapshots where present. A latest available
source snapshot and the first verified interval bracket first passage.
Take a source snapshot at least every minute during normal operation.

**Validation.** Restore source to a fresh writable copy with the same
read-only upstream dependencies, discard participant build products, build
and import each claimed target, check its type and transitive axioms. Compare
the mathematical signatures and definitions against the packet; definitions
of the desired numerical answer do not satisfy the quotient/image requirement.
Use per-declaration checking for authentic partial progress even when the whole
library does not build. A–E do not prescribe a single Lean signature. For an
arm's separately frozen challenge, check whether its own comparator passed
and report that separately. The common result is the semantic and kernel
review. Use opaque IDs and code-only review packets for semantic review,
then reveal assignment; recognizable style may still reveal the framework.
The supervisor's finite oracle tests only finite cases, not the general theorem.

**Interpretation and stopping.** Each run's own unsuccessful proof attempts,
early stopping or organizational delay stay in the record. Infrastructure
failures before mathematical work are repaired and restarted on a new clean
room. Failures after exposure are logged with cause, and labeled replay runs
are reported separately from the original. No protocol or packet changes
after exposure; no mathematical hints by the supervisor. One stage comparison
and a four-run table answer this particular case, with no population-level
significance claim.
